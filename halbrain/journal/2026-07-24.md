### [14:04] Unit-cost analysis per user — two structural cost bugs found (branch: develop · commits: none, analysis only)
**Synopsis:** User asked what HAL costs per user to run, for pricing. Measured the actual call patterns in code, then verified live 2026 pricing for X API and xAI. Found the cost is ~95% X API sync waste, and that the app runs a **legacy model that costs more than xAI's newest flagship**.
**What worked + Evidence:** Grounded every driver in code rather than estimating blind:
- **X API is the dominant cost and it's structural waste.** `api/sync/background/route.ts:66` hardcodes `max_results=100`; Guard 5 (`:91-93`) breaks after page 1 once `newestKnownId` appears. So a routine incremental sync re-reads a **full 100 bookmarks to discover 0-2 new ones**. X bills owned reads (`GET /2/users/{id}/bookmarks`) at **$0.001 per resource returned** (docs.x.com/x-api/getting-started/pricing, Owned Reads, effective 2026-04-20) → **~$0.10 per sync**. `lib/use-auto-sync.ts:10` throttles at only **2 minutes** and fires on app open + every resume → ~5 syncs/day ⇒ **~$15/user/month**. Fix: drop `max_results` to ~10 on caught-up syncs (guards already paginate when there *is* new data) + widen the throttle; cuts this ~10× to ~$1.50.
- **grok-3 is more expensive than grok-4.5.** `lib/grok.ts:11` defaults `MODEL_FULL='grok-3'` and `enrichBookmarkLLM` (`:148`) uses it for **every** bookmark. Per docs.x.ai/developers/pricing: grok-4.5 = **$2.00/M in, $6.00/M out** (cached in $0.30); grok-4.3 = $1.25/$2.50 + 20% Batch discount. grok-3 (secondary source, mem0) = **$3.00/M in, $15.00/M out** — and grok-3 is **absent from xAI's current pricing table entirely**, so it's legacy and a continuity risk, not just a cost one. Switching to grok-4.5 is simultaneously cheaper (~48% on classification) and more capable; grok-4.3+Batch is cheapest.
- **Tier 1 regex does NOT save the LLM call** — `classifyBookmark` (`:200-235`) always calls `enrichBookmarkLLM`; regex only fills category/domain. So classification = 1 full-model call per bookmark (~500 in / ~120 out tokens: system prompt is schema + the 54-tag `TAG_TAXONOMY` + rules ≈ 355 tokens, content capped at 500 chars by `sanitizeForLLM:92`).
- Assistant chat is the other real driver: `buildBookmarkContext` injects `SEARCH_MATCH_LIMIT=40` matches + `RECENT_SLICE_LIMIT=8` recent + tags + folders ⇒ ~5.5K input tokens **per message**.
- Modelled typical user from [[knowledge/orientation]]'s own target profile (10-50 saves/week).
**What did NOT work:** Could not measure real token counts — `grok.ts:20` declares `usage {prompt_tokens, completion_tokens}` in `ChatResponse` but `chat()` discards it, returning only `content`. All token figures are engineering estimates from prompt structure, not measured. Also unresolved: whether the `expansions=author_id` user objects (`route.ts:68`) bill separately as "User: Read" at **$0.010/resource** — if they do, a 100-bookmark page costs ~$1.10 not $0.10, a 10× blowup.
